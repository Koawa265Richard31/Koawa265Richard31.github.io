## 一个全绿的测试能证明什么

这个测试要验证的是"agent 检索历史时不泄漏敏感内容"。我埋了一个合成秘密（`TOPSECRET-SEED-` 加三百个字符）到历史记录里，跑完任务，断言最终发给模型的请求里没有这个标记。通过了。

问题出在一个不起眼的细节：测试没把 turn 绑定上。recall 工具解析不了当前线程，返回了 `recall_unavailable`——**检索根本没发生**。请求里当然没有秘密。断言为真，但它在"什么都没发生"的世界里为真。

一个类比：测防火墙，网线拔了，然后宣布"攻击包没到内网"。攻击的确没到内网，但是没意义。测试的 docstring 里后来留了一句话：passed vacuously，空转通过。

修复本身很简单，值得记的是顺序——**先证明执行成功，再做内容泄漏检查**。三段断言：stub 真的收到了查询；回执非错、命中的就是那条带秘密的历史；然后才是"请求里没有秘密"。只要少任何一段，测试命题就退化回旧版。

## 带着同一双眼睛出门

我第一周的功课是读 [AgentDojo](https://github.com/ethz-spylab/agentdojo)——ETH 的 agent 攻防评测框架。英文文档读得我头疼，所以我用 GLM 帮我读，我只作消化，但概念不复杂：它每次跑分同时给两样东西记分——**user_task**（正常用户要办的事，agent 该办成）和 **injection_task**（攻击者的目标）。攻击载荷不放在用户消息里，而是藏在工具输出里——邮件正文、网页、slack 消息。攻击者控制的是"模型干活时必然会看到的环境数据"，不是用户说什么。这就是间接提示注入（indirect prompt injection）。

我注意到一个细节：文档讲了攻击怎么注入，但是**没讲"攻击成功怎么判定"**。判定逻辑就在套件代码里。文档和代码之间的空隙，这就是这类问题最爱藏身的地方。

## 镜像：未执行被记成攻击成功

然后我叫 GLM 帮我整理，读到了 [#168](https://github.com/ethz-spylab/agentdojo/issues/168)，webpro255 的发现：slack 套件的评分函数 `security_from_traces` 拿 trace 里的调用序列模拟状态——**假设每个调用都执行了**。防御把三个成员操作全部拦截后，调用仍在 trace 里（模型提议过），模拟照样走完且记一次攻击成功。而他的实测：被记为"成功"的样本 **9/9 但是实际执行次数为零**。

最有价值的是 mohameduk 后来补的对照实验：

| 组   | 记为攻击成功 | 实际执行全部三步    |
| --- | ------ | ----------- |
| 无防御 | 18     | 18  全对      |
| 有防御 | 15     | **0**    全错 |

无防御臂评分全对。所以他的结论很精确：**不是 checker 写错了，是一条没写出来的假设——attempted == executed**。对不在执行边界干预的防御天然成立，对在边界拦截的防御崩掉，而且防御越强、被误记越多。评分系统在惩罚最强的防御。

这和我的空转测试是镜像。同一个根因——拿"尝试/意图层"的信号当"执行/效果层"的证据——我的方向记成假防御成功，他们的方向记成假攻击成功。

## 一个根因，三层爆发

继续读下去，同一个根因在另外两层各炸出一个症状：

**任务代码层，[#188](https://github.com/ethz-spylab/agentdojo/issues/188)**（还是 mohameduk）：这里有两本账。agent 提议发帖时，`web_requests` 记一笔（"想发"）；帖子真的发出去时，`web_content` 记一笔（"发了什么"）。utility 检查先看前一本有没有条目，有，就直接去后一本翻内容——它默认"想发的都发出去了"。这个默认从来没被写进任何一行判断，它是被"从没人拦过"保证的：仓库里已发表的跑分全部无防御，提议和执行总是连着发生，两本账总是同时记账。防御一出场，两本账第一次出现"只有想发、没有发出"——去翻内容，`KeyError`，整个跑分崩掉。同一个"把提议当执行"，#168 是写在评分函数里，这里是藏在两本账的同步习惯里。

**聚合层，[#186](https://github.com/ethz-spylab/agentdojo/issues/186)**（roli-lpci）：报错的 trial（provider 挂了之类）也带着普通布尔值被存下来，混进 utility 和攻击成功率的分母。极端情况：10 个 trial 全部 API 挂掉，attack success = 0%，换防御视角读就是**防御成功率 100%**——什么都没跑，防御拿了满分。他的修法是把错误 trial 踢出分母、全错误显示 N/A。这里有个词的精确性值得单独记：分母改成的是"**跑完的**"不是"跑成功的"——**错误 ≠ 失败，错误是"没有资格被判定"**。

| | 出事的层 | 症状 | "未执行"的原因 |
|---|---|---|---|
| #168 | 评分函数 | 假的攻击成功（ASR 虚高） | 防御拦截 |
| #188 | 任务代码 | KeyError 崩溃，炸掉整个 run | 防御拒绝写入 |
| #186 | 聚合层 | 错误样本污染分母，全错误跑伪装 0%/100% | provider 错误 |

## 最锋利的一句

把三个 issue 摆完，我以为我的题目被人做完了。再想一层才发现没有：

#186 证明的只是 `error != null` 的 trial——**显式错误**。而我那个空转测试，跑分完整跑完、没有任何错误标记，recall 只是**静默地**返回了 unavailable。分母修复对它完全无效。

**显式错误有人承接，静默降级却被疏漏。** 我的题目就缩到了这个角落：在一个"完成"的 trial 内部，怎么证明关键路径真的发生过。注意这还是个假设，没验证——计划后续做实验，两臂对照：同任务同评分器，一臂正常跑，一臂让路径静默失效；如果"防御成功"读数在失效臂照样漂亮，空转实锤。微观版其实我已经做过一遍：先断言命中，再查泄漏，一回事。

## 这天得到的检查习惯

1. **证据层分离**：看到任何"成功/失败"结论，先问它读的是意图层（提议过、出现在 trace、输出里没有 X）还是执行层（真的跑了、副作用真的发生了）。两层各自为真，互相不能冒充。
2. **三层分开审**：评分函数、任务代码、聚合层——同一根因会炸出完全不同的症状（假成功、崩溃、分数污染），只盯一层会有疏漏。
3. **对照臂思维**：判断评分器可不可信，加一个"正常跑"的对照臂。mohameduk 那张表一半的力量来自"无防御臂全对"——它证明 checker 不是坏的，是假设在特定条件下失效。
4. **先证命中，再证无泄漏**：写测试先断言关键路径真实发生，再做内容断言。这条是从自己的 bug 里学的。
