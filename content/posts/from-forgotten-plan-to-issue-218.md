[上一篇](/posts/evaluation-vacuous-pass/)的结尾我说：做完了回来写第 2 篇。做完了，这是第 2 篇。结果是：[issue #218](https://github.com/ethz-spylab/agentdojo/issues/218)——我对 [AgentDojo](https://github.com/ethz-spylab/agentdojo)（ETH 的 agent 攻防评测框架）提交的第一个 issue：一个确定性的复现，证明它的任务判定可以被"零执行的运行"骗过，外加对在飞修复 PR #207 的压力测试。从翻出计划到点下提交，四天。

## 一、起点：一份我不记得的计划

九月三十日，我的仓库里多了一份文档：《Agent 安全社区贡献与 KoawaAgent 学习路线》，8 周计划，带每周门槛和披露纪律。问题是我对它没有印象——后来查时间线和提交记录才确认，它是某个并行会话在我指导下写下的，我驱动了讨论，但没有亲眼看过产物。

我把它从头读了一遍，决定照着执行。计划本身写得很清楚：每周约 10 小时、一次只做一个问题、一切对外发送需要我逐次授权、不把维护者没回复当拒绝。第一周的门槛是"能用自己的话讲清上一篇博客里那个空转案例"。我在带读模式下过了这个门槛，那一周的记录在这里不展开，一句话：我签下了自己的预测——**纯 trace 判定会把没执行的调用当成任务完成**。

## 二、环境与基线：开箱即红

第二周搭环境。三个坑，都记进了复现记录：我平时用 PowerShell 而不是 Bash，语法不一样；pip 走的镜像源对这个包 403，换官方源加代理解决；AgentDojo 官方只支持 Python 3.10–3.12，我机器上的 3.13 不在列表里。最后是 codex-runtime 的 3.12 建的独立 venv，装 `agentdojo==0.1.35`，一切和两个代码仓库隔离。

然后跑它自带的体检 `suite.check()`，结果开箱即红：40 个任务全部报 "The task is not injectable"。这是一个很好的归因练习。我先赌"套件版本太旧"，换到最新版 v1.2.2——还是红，同样的话，**假设被证伪**。再看结构：注入任务全绿说明执行机器没坏，40 个任务同一条消息说明是某个子检查在批量失败。用 `check_injectable=False` 这个开关把子检查隔离出去——utility 主链路 40/40 全绿。结论：坏的是"注入可达性"检查本身，不是任务，不是我的安装。顺带学到一件事：**总判定是 False，明细里 40 个任务全是 True——读结构化明细，别读标题布尔。**这个现象本身也记进了 issue 的素材库。

## 三、两条判定路，三臂实验

读 `task_suite.py`，任务判定有两条路：`utility_from_traces`（从调用记录模拟，A 路）和 `utility`（环境前后对比，B 路）。A 路是基类文档认可的标准写法，"适用于不在环境里留痕的任务"。全库 grep：默认套件里走 A 路的任务只有一个——slack 的 user_task_11，"邀请新同事 Dora"。

于是写实验装置。核心是一个约 60 行的"黑洞执行器"：对选定函数，提议消息照发（所以它会进入 traces）、伪造一张回执、跳过真实执行；其余步骤正常执行。下游依赖被破坏的调用会以可见的错误回执失败——`add_user_to_channel` 报 "User Dora not found"，这个报错同时独立证明了执行确实没发生。

三臂跑完，和我登记的预测一字不差：

| 臂 | 判定 | 结果 |
|---|---|---|
| 对照（正常跑） | 原版混血判定 | True |
| 静默失效 | 原版混血判定（含环境检查） | **False**，被作者自加的环境检查救下 |
| 静默失效 | 纯 trace 判定（文档认可的写法） | **True**——零执行，判为任务完成 |

第一周的预测在这时候兑现了。

## 四、战场变了：从发现者到验证者

发送前按计划做重复项终检。我的角度干净：全库搜 `utility_from_traces`，零提及。但出现了新情况：[PR #207](https://github.com/ethz-spylab/agentdojo/pull/207)，open，有人在实现修复——给 `FunctionCall` 加 `executed` 字段，由回执派生（回执没报错就算执行了）。[#168](https://github.com/ethz-spylab/agentdojo/issues/168) 讨论串里 zingnan527 提议的就是这个。

这改变了我的定位。我本来要提议的修复已经有人在做了，再提就是重复。但读完 #207 的 diff，发现它留下两道缺口，而我的装置恰好能验证——于是从"发现者"变成"验证者"：帮在飞的修复收尾，比另开一个报问题的帖子有用。

## 五、2×2：两道缺口

装置加了两个旋钮：回执诚实性（诚实报错 / 假成功）、评分器风格（纯 trace / 自觉查 executed——后者是遵守 #207 新文档要求的写法）。同一个静默失效运行，四格：

| | 纯 trace | 查 executed |
|---|---|---|
| 诚实报错 | **True**（缺口一） | False——修复在这种世界里有效 |
| 假成功 | True | **True**（缺口二） |

缺口一：`executed=False` 就挂在调用对象上，纯 trace 评分器不读它——文档说的"不得"是劝告，不是强制。缺口二：`executed` 是回执说了算的，谎报成功的回执直接把它骗成 True——**回执是证词，不是勘验**。一句话总结：**#207 修好了数据可得性；回执撒谎或评分器不查，任破一个，空转就换个形式回来。**

## 六、写作与发布

报告用英文写成独立 issue（比我原想的"在 PR 下评论"更显眼，也方便维护者追踪），七段结构：背景、复现设置、两个发现、建议、局限、分工声明。发布前我把全文换成中文逐段审读——每一段都要能用中文复述出它主张什么、证据是哪次实验，复述不出的段落回去改。审完，我下了发送指令。脚本挂在公开 [gist](https://gist.github.com/Koawa265Richard31/6e82460e7561e607535222dcf13d598a)，链接在 issue 里。

现在进入待响应期。计划里写过：维护者无响应不等于拒绝——这个仓库已经沉寂四个月，#168 挂了三个月没人理，这是已知背景。不催，不重复提交。

## 七、这次带走的

1. **预测先行**。每条命令跑之前先赌结果，错了最有价值——四天里我登记的预测（基线不会全绿、三臂的 False/True、2×2 的两格）全部对上了，这不是运气，是被迫想清楚的表现。
2. **单变量对照**。臂与臂之间只差一个旋钮，分数差异就没有第二个可以背锅的原因。
3. **读结构化明细，别读标题布尔**。这件事四天里撞见了两次。
4. **主张分两类**："这种车型设计有缺陷"（机制级）和"路上有车正在出事"（现状级）——第二个要用全量清点排除，我 grep 了两遍才敢说"默认套件目前没有任务在空转"。
5. **诚实边界是最强的防守**。issue 里明写"#207 的语义是我在旧版本上模拟的，应在 PR 分支复跑确认"。这种句子不是示弱，是让报告里剩下的每一句话都打不倒。

## 分工说明

和上一篇同样的口径，诚实起见：

- **Agent 做的**：源码检索与定位、实验装置代码（黑洞执行器、2×2 脚本）、英文 issue 初稿、本篇博客初稿（按我的口吻，我指示的）。
- **我做的**：每一条命令都由我本人运行（环境搭建、基线、三臂、2×2 都是）；所有预测由我独立作出；报告逐段中文审读验收；发送指令由我下达——文责在我。
- **上游作者的**：#168 的发现（webpro255）、对照实验（mohameduk）、`executed` 字段提议（zingnan527）、#186（roli-lpci）、#207 的在飞实现。我的部分是对任务侧的验证和对修复的补充，不冒领任何一项。

四天前我不记得那份计划的存在。今天我有了一个被自己每一行证据支撑着的 issue。8 周计划走到这里，第 1 到第 4 周的内容全部完成——剩下的，等维护者的回复，和下一篇（R1-R5 的正文，还在我自己的待写清单上）。
